# Walking Skeleton — Ranker

**Phase:** 1
**Generated:** 2026-11-21

## Capability Proven End-to-End

A visitor opens `https://<PUBLIC_HOSTNAME>/` and the Next.js page, served through Caddy, calls FastAPI on the same origin. They see live pass/fail checks for the API, Postgres, the pgvector version (read from `pg_extension`), the baked embedding model (a 384-dim probe embedding) and a signed-cookie round-trip. The same stack starts locally with `make dev`.

## Architectural Decisions

| Decision | Choice | Rationale |
|---|---|---|
| Backend framework | FastAPI 0.165 (plain `fastapi` + `uvicorn[standard]`, not `fastapi[standard]`) on Python 3.14, run with uv | Native SSE for Phase 5; `[standard]` now pulls in the OpenTelemetry SDK and other unused packages. 3.14 is the newest Python with onnxruntime wheels. |
| Backend layout | uv flat layout: `backend/ranker/` package with `api/` routers, `db/`, `embeddings/`, `services/` (Phase 4), `llm/` (Phase 2), `tasks/` (Phase 2), `worker/` (`python -m ranker.worker`), `observability.py`, `settings.py`, `selfcheck.py` | Follows SPEC §16 and the ARCHITECTURE.md boundaries, so later phases add modules without restructuring. |
| URL contract | Every API route lives under `/api` (`/api/healthz`, `/api/readyz`, `/api/session/ping`, `/api/docs`, `/api/openapi.json`). Next.js has no `app/api` handlers. | D-06. Caddy passes `/api` through unchanged, and dev mirrors this with a Next rewrite. |
| Frontend | Next.js 16.4 App Router, React 19.3, TypeScript ~5.9.3 (never 7.x), Tailwind 4 CSS-first, shadcn/ui, `output: "standalone"`, under `web/src/` | FND-02 pins. Standalone runs in its own container (D-05). |
| Data layer | PostgreSQL 18 + pgvector 0.8.7 (`pgvector/pgvector:0.8.7-pg18-trixie`) everywhere: dev, CI testcontainers, prod. SQLAlchemy 2.1 async + psycopg 3, Alembic migrations (0001 = `CREATE EXTENSION vector`). Volume at `/var/lib/postgresql`. | One datastore. pgvector ≥ 0.8.3 fixes HNSW-vacuum corruption. The PG18 volume path changed from earlier versions. |
| DB read / write in the skeleton | Read: `SELECT extversion FROM pg_extension WHERE extname='vector'` in readyz. Write: the Alembic migration (`CREATE EXTENSION`, `alembic_version`) on every deploy. | No app tables until Phase 2 (jobs). The migration path is exercised from day 1. |
| Embeddings | fastembed 0.9.1 `BAAI/bge-small-en-v1.5` (384-d, quantised ONNX) baked into the API image at `/opt/models`, `HF_HUB_OFFLINE=1`, `EMBED_THREADS=2`. `Embedder` protocol with `FakeEmbedder` for tests. | FND-05: no network at startup, proven by `docker run --network none … ranker.selfcheck` in CI. Tests never hit Hugging Face. |
| Auth / session | No auth in Phase 1. Signed HttpOnly, Secure, SameSite=Lax test cookie `rk_ping` (itsdangerous, `SESSION_SECRET`) proves same-origin cookies work in production. | D-21. Real guest sessions (opaque DB-backed tokens) arrive in Phase 4. |
| Topology | Single origin: Caddy serves `https://<host>/` → web:3000 and `/api/*` → api:8000 (`flush_interval -1`, no compression on `/api`). No CORS. | D-04/D-07. Removes PSL/SameSite cookie problems, works with a free DuckDNS name, and is SSE-safe for Phase 5. |
| Deployment target | One Ubuntu 24.04 VM (DigitalOcean BLR1 4 GB by default; GCP/Oracle/Hetzner fallbacks), Docker Compose (`deploy/compose.prod.yaml`): caddy, web, api (1 uvicorn worker), worker, db (no published port). Set up only by `deploy/bootstrap.sh`. | D-02/D-08/D-09. Provider-agnostic, near-$0 with Student Pack credit. |
| Hostname | One env var `PUBLIC_HOSTNAME`, never hard-coded (registrable Student-Pack domain or DuckDNS) | D-03 |
| CI/CD | One GitHub Actions workflow: backend (ruff, pyright, pytest on testcontainers), web (eslint, tsc, build), deploy-config checks, images (offline selfcheck, push to GHCR `ghcr.io/ayushmaurya-tech/ranker-{api,web}:sha-<7>`), then a secrets-gated SSH deploy that runs `deploy/deploy.sh` (pull → migrate → up --wait) and `deploy/smoke.sh`. `make deploy` is the manual fallback. | D-12/D-13/D-14. CD auto-skips until secrets exist. |
| Secrets & config | pydantic-settings from env only. Prod secrets in `/srv/ranker/.env` (mode 600, generated by bootstrap). `.env.example` documents every variable, with a test guarding Settings coverage. | D-10, SEC-07 |
| Logging | structlog JSON for all processes via `ranker.observability.configure_logging`. Request IDs come from asgi-correlation-id. A redaction processor (keys resume_text, message, content, email, password, authorization, cookie, …) sits last before JSON rendering, with `show_locals=False`. There is no uvicorn access log; a request-log middleware records the path only. | D-22, SEC-07, OPS-04 |
| Worker | `python -m ranker.worker`: asyncio loop with heartbeat and a SIGTERM/SIGINT clean exit. No model loaded. | D-08. Phase 2 adds APScheduler (<4) and the `tasks` consumer inside the same loop. |
| Local dev | `make dev` = `docker compose -f compose.yaml -f compose.dev.yaml up --build` (bind mounts, `--reload`, `next dev`, loopback ports, Next rewrite `/api` → api:8000). Native path is `make db` + `uv run` / `npm run dev`. | D-15/D-16 |

## Out of Scope (Deferred to Later Slices)

- Ingestion, normalisation, embeddings of jobs, LLM gateway, `tasks` queue, scheduler jobs (Phase 2)
- Search endpoint, search UI, rate limiting, eval harness (Phase 3)
- Guest sessions and auth, resume upload, ranking, CSRF, security headers beyond Caddy's HSTS, nosniff and referrer policy (Phase 4)
- Chat/SSE agent, memory, Sentry and uptime monitoring (Phase 5)
- Backups and restore runbook, Prometheus `/metrics`, accounts (Phase 6)
- Vercel / preview deployments (not planned: single-origin decision D-04/D-05)
- Multi-arch images by default (`PLATFORMS` variable switches to arm64 only if the Oracle fallback is used)

## Subsequent Slice Plan

Each later phase adds one vertical slice on top of this skeleton without changing its architectural decisions:

- Phase 2: Production holds a fresh, embedded index of real tech jobs refreshed by the worker; the LLM gateway and `tasks` queue exist.
- Phase 3: A guest types a natural-language query on the landing page and gets filtered, fresh, hybrid-ranked jobs; eval gate in CI.
- Phase 4: A visitor uploads a resume, edits the profile and gets a personalised, explained feed that reacts to save/skip, with degraded mode.
- Phase 5: A user chats with a grounded, streaming agent that remembers preferences; the MVP launches with monitoring.
- Phase 6: v1 completion: richer index, learning personalisation, accounts, public evals, production ops, real users.
